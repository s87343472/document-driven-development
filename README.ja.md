## ドキュメント駆動開発とは

**ドキュメントこそが唯一の真実の源（Single Source of Truth）。コードはドキュメントの実装であり、その逆ではない。**

エージェントに「登録ページを作って」と言うと、エージェントは*自分の理解した*バージョンを完璧に実装します——あなたが口にしなかったセキュリティ、エッジケース、ビジネスルールの前提を、すべて学習データの平均値で埋めて。自然言語は本質的に曖昧です。人間同士は共有経験で行間を補いますが、あなたとエージェントの間にその共有文脈はありません。

このスキルは、曖昧な要件から AI に直接コードを生成させる代わりに、次の順序へ導きます：

1. **まず考える** —— 意図・スコープ・成功基準を明確化する
2. **次に文書化する** —— 構造化されたドキュメントを作る
3. **最後にコードを書く** —— 明確な仕様に基づいて生成する

成果物は Web アプリとは限りません。スキル、エージェント、MCP サーバー、CLI ツール、.md 方法論も、すべて同じドキュメント体系で扱えます。

## コアの公式

```
intent.md  →  roadmap.md  →  spec.md  →  plan.md  →  コード
（なぜ）      （道筋）       （何を）      （どう）
```

- **生成は安価、制御された進化は希少。** ボトルネックはもはやコードを書くことではなく、何が存在すべきかを決めること——その決定の場がドキュメントです。
- **問題はドキュメントまで遡る。** コードが失敗したら、真実の源を直してから再生成する。
- **欲しいものの描写 ≠ 作るべきものの定義。** Spec が前者を後者に変えます。

## ドキュメント体系

| レイヤー | ファイル | 答える問い | 安定性 |
| -------- | -------- | ---------- | ------ |
| 意図層 | `intent.md` | なぜ・誰のために | めったに変わらない |
| ロードマップ層 | `roadmap.md` | バージョンの道筋 + 不変のアーキテクチャの背骨 | 時々（複数バージョン製品のみ） |
| 仕様層 | `spec.md` | 何を作るか | 機能ごとに変わる |
| 計画層 | `plan.md` | 技術的にどう作るか | 頻繁に変わる |

以上はビルド時ドキュメントです。エージェント型プロダクトには**ランタイムドキュメント**——動作中のプロダクト自身が読み書きする標準 / 記憶 / 状態ファイル——も存在しえます。バージョン管理し、人間が読める形に保つことで、プロダクトが「どう考えているか」をユーザーが確認・編集できます。詳細は [`principles.md`](skills/document-driven-development/principles.md) を参照。

## インストール

### Claude Code の場合

```bash
# プロジェクト内
mkdir -p .claude/skills
cp -r skills/document-driven-development .claude/skills/

# またはグローバルに
cp -r skills/document-driven-development ~/.claude/skills/
```

### Claude（Web / API）の場合

`skills/document-driven-development/SKILL.md` の内容（コンテキストに余裕があれば `templates.md` と `principles.md` も）をシステムプロンプトまたはプロジェクト指示にコピーしてください。

## 使い方

インストール後、以下の場合に Claude がこの方法論を適用します：

- DDD でプロジェクトを構築するよう明示的に依頼したとき
- 既存プロジェクトへの機能追加を依頼したとき
- `intent.md`、`spec.md`、`plan.md`、`roadmap.md` に言及したとき

注意：過剰なトリガーを避けるため、スキルはデフォルトで `disable-auto-invoke: true` を含みます。自動的に有効化したい場合は、SKILL.md の frontmatter からこの行を削除してください。

## ビフォー・アフター

### Before: Vibe Coding

```
あなた：個人ブログを作って
Claude：了解！[500 行のコードを生成]
あなた：待って、もっとシンプルに。DB なし、markdown ファイルだけで……
Claude：では作り直します……[さらに 500 行、まだ何か違う]

# 結果：何度もやり直し、時間の浪費、期待と一致しないコード
```

### After: ドキュメント駆動

```
あなた：個人ブログを作って
Claude：ドキュメント駆動開発でいきましょう。まず質問です：
  1. 主な目的は？ 2. 読者は誰？
  3. v0.1 の「完成」とは？ 4. 作らないものは？

あなた：技術記事の共有、読者は開発者。v0.1 は markdown の
    レンダリングだけ。コメント・CMS・DB は不要。

Claude：[intent.md、spec.md、plan.md を作成してから、的確なコードを生成]

# 結果：一発で正解、今後のイテレーションのためのドキュメントも残る
```

## 基本原則

1. **ドキュメントが先、コードが後** —— 明確なドキュメントなしにコードを生成しない
2. **問題はドキュメントまで遡る** —— コードが失敗したら、spec の問題か plan の問題かを確認
3. **1 バージョンにつき 1 つのコア目標** —— v0.1、v0.2、v0.3……小さく進む
4. **ドキュメントとコードを同期させる** —— 一緒にコミットする
5. **ドキュメントはコミュニケーションのため** —— 未来の自分と AI のために書く
6. **v0.1 の前にアーキテクチャの背骨を定義する** —— バージョンをまたいで変わらない部分を名指しすることで、薄い v0.1 が使い捨てにならない
7. **各バージョンに検証ゲートを設ける** —— ツールなら「仕様どおり動くか」。プロダクトならリテンション・利用・課金という現実のシグナル（「興味がある」では不十分）。ゲートを通過するまで次に進まない
8. **エージェント型プロジェクトでは、ドキュメントがランタイムにもなりうる** —— エージェントが実行時に読み書きする。人間が読める形でバージョン管理する

## ベストプラクティス

### やるべきこと

- **intent.md から始める** —— 5 行でも、ないよりずっと良い
- **非目標を明示する** —— 「ユーザーアカウントは作らない」がスコープの肥大化を防ぐ
- **v0.1 の前に背骨を名付ける** —— 後続バージョンはそれを埋めるのであって、作り直すのではない
- **バージョンを小さく保つ** —— v0.1 は数日ではなく数時間で達成できる規模に
- **要件が変わったらまずドキュメントを更新** —— コードだけでなく真実の源を直す
- **ドキュメントとコードを一緒にコミットする**

### やってはいけないこと

- **いきなりコードに飛びつかない** —— 「とりあえず書き始める」衝動に抗う
- **過剰に文書化しない** —— plan.md は達成すべきことを書く場所で、コードの逐語ではない
- **spec.md に技術選定を書かない** —— 「ユーザーが検索できる」（良い）vs「Elasticsearch を使う」（plan.md へ）
- **いきなり v1.0 を目指さない** —— v0.1 → v0.2 → v0.3 が正道
- **ゲート未通過のまま進まない** —— 検証されていない仮定の上に建てることになる

## FAQ

**Q: AI に直接コードを書かせるより遅くないですか？**
些末なタスクなら遅いです。しかしイテレーションするものなら違います。ドキュメントに費やした時間は、「これじゃない」ループを回避することで何倍にもなって返ってきます。

**Q: すべてのドキュメントが必要ですか？**
小さなプロジェクトでは統合しても構いませんし、roadmap.md は複数バージョン製品でのみ意味を持ちます。ただし分けて書くことで、なぜ → 道筋 → 何を → どう、と異なるレベルで考えられます。

**Q: プロジェクト途中で要件が変わったら？**
まずドキュメントを更新し、次にコードを更新します。ドキュメントを常に真実の源に保ちます。

**Q: Claude 以外の AI ツールでも使えますか？**
使えます。この方法論はあらゆる AI コーディングアシスタントで機能します——SKILL.md をシステムプロンプトにコピーしてください。
